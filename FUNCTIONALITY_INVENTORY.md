# PDF Elite — Functionality Inventory (Phase 0)

Baseline map of every **visible viewer control** in the active UI: where it is defined, what it calls, and whether it performs a real operation. This is the reference the 39-phase refinement works against. Status legend:

- **REAL** — wired to a genuine implementation and works.
- **PARTIAL** — wired, but incomplete or fed mock/hardcoded data.
- **VISUAL** — renders but does nothing real (dead / decorative / fake data).

> Architecture note: the app renders the **real** `EmbedPdfViewer` (`components/viewer/`) *inside* the newer reskinned shell `workbench/viewer/ViewerShell`. Wiring chain: `pages/HomePage.tsx` → `components/viewer/Viewer.tsx` → `workbench/viewer/ViewerShell` (passes `EmbedPdfViewer` as `children`). The single scroll owner is the `@embedpdf` `<Viewport>` in `components/viewer/LocalEmbedPDF.tsx` (`overflow:auto`); everything above it clips (`overflow:hidden`).

## Phase 4–7 notes

- **Phase 4 (page navigation):** No code change required — the always-visible `ViewerLeftRail` page field (`N / total`) is already REAL. Type + Enter/blur jumps, invalid input reverts, and it re-syncs from `currentPage` on every source (scroll, Prev/Next, bookmark/outline nav, tab switch) because all of them route through `scrollActions.scrollToPage` → `registerImmediateScrollUpdate`. The Inspector Pages tab is a secondary synced scrubber (closed by default since Phase 3), driven by the same source of truth — not a competing control.
- **Phase 5 (zoom sync):** Fixed the toolbar zoom slider unit mismatch — it emitted a *scale* (0.25–5) while `ViewerShell` divides by 100 (expecting a *percent*), so dragging set ~1% zoom. Slider is now percent-domain (`25–500`, `value={Math.round(zoom.percentage)}`) matching the `setZoomLevel(percent/100)` convention used everywhere. Percentage readouts rounded. All zoom sources funnel through `zoomActions` → `registerImmediateZoomUpdate`, so every control stays in sync. The Comment-mode mini zoom reads the same synced state (not a separate system).
- **Phase 6 (touchpad pinch):** Fixed `getZoomFactor` in `EmbedPdfViewer` from `zoomPercent / 75` to `/ 100`. It must return the current zoom as a scale factor matching `setZoomLevel` (1.0 = 100%); `/75` reported 1.333 at 100%, so the first pinch tick snapped zoom to ~133% before applying the gesture delta. Pinch/ctrl+wheel already route through the real `useWheelZoom` → `zoomActions.setZoomLevel` (no secondary engine). **Requires verification on the real Windows touchpad.**
- **Phase 7 (text selection):** Selection is enabled in reading mode (embedpdf `<SelectionLayer>` + `textSelection: true`; view mode uses the passive `"select"` tool). Removed the duplicate workbench `TextSelectionPopover` so the single real embedpdf `TextSelectionMenu` governs selection — it applies actions to the live selection and includes Copy + Comment. **Two-popover overlap gone; verify visually in the running app.**

## Phase 8–11 notes (annotation apply + color)

All four edits are in the single annotation effect in `workbench/viewer/ViewerShell.tsx` (the `useEffect` on `[tool.tempTool, tool.highlightColor, ...]`), reusing the real `components/viewer/AnnotationAPIBridge` — no new annotation machinery was introduced.

- **Phase 8 (highlight application):** Highlight already applies a real `PdfAnnotationSubtype.HIGHLIGHT` to the live text selection through two real paths: the embedpdf `TextSelectionMenu` (`setActiveTool("highlight")` consumes the current selection) and the toolbar Highlight button (`activateAnnotationTool("highlight")`). Both create persistent document annotations, and `deactivateToolAfterCreate:false` keeps the highlight tool armed for consecutive passages while `selectAfterCreate:true` keeps the new annotation visible/selected. **Verify visually in the running app** (annotation apply is interactive; not confirmable from source alone).
- **Phase 9 (highlight color) — real bug fixed:** The picker set `tool.highlightColor` (persisted to `localStorage pdf-elite:highlight-color`), but the color never reached the applied annotation: the embedpdf `TextSelectionMenu` calls `setActiveTool` with **no** color (always the registered default `#ffd54f`), and `activateAnnotationTool` sets the active tool (consuming the selection) **before** applying `setToolDefaults`, so a selection-first highlight used the *previous* color. Fix: the effect now calls `setAnnotationStyle("highlight", { color })` on every run — this sets the highlight tool's **default** without activating/consuming the selection, so the chosen color reaches **both** entry points and the ordering bug is moot. Palette stays compact/contextual (only rendered when `tempTool==="highlight"`) and is never reset after use.
- **Phase 10 (area highlight) — rewired:** `area-highlight` mapped to the freehand `inkHighlighter` (INK) — a scribble, not an area. Rewired to the real `square` tool (`PdfAnnotationSubtype.SQUARE`): drag to size with a live preview, Escape cancels the in-progress drag, `deactivateToolAfterCreate:true` returns to a sensible tool state, and it persists as a real SQUARE annotation. Styled as a translucent highlight (fill+border = highlight color, ~0.3 opacity). This reuses existing SQUARE support rather than inventing a tool. **Verify visually** (drag/preview/escape are interactive).
- **Phase 11 (underline / strikethrough):** Both apply real `UNDERLINE` / `STRIKEOUT` annotations to the live selection. Removed the incorrect `{ color: tool.highlightColor }` override so they use their own readable defaults (underline `#ffb300` amber, strikeout `#e53935` red) — matching what the embedpdf `TextSelectionMenu` applies, so the toolbar and the selection menu are now consistent. **Verify visually.**

All edits are in `workbench/viewer/ViewerShell.tsx` (the annotation `useEffect`, the keydown effect, the ContextualToolbar mount, and the Comment-mode panel JSX/CSS) plus one line in `workbench/viewer/ContextualToolbar.tsx`. No new annotation/editor machinery — everything reuses the real `AnnotationAPIBridge` tools and the app's canonical `handleToolSelect` router.

- **Phase 12 (comments & notes) — real bug fixed:** The Comment-mode "Sticky note" activated `activateAnnotationTool("textComment")`, but `"textComment"` is **not** a registered tool in this viewer (`LocalEmbedPDF.ensureTool` registers `note`, not `textComment`), so clicking Sticky note did nothing — the Comment-mode failure the plan references. Fixed by activating the **real** `"note"` tool (a FREETEXT sticky with `clickBehavior` click-to-place, `defaultSize` 160×100, `selectAfterCreate`): click a spot → note is created and opens for typing. The "Text comment" tool previously forced `tool.highlightColor` as the **font** color (near-invisible pale-yellow text on white); removed the override so it uses its own readable default. Also **removed the fabricated comment panel** — the hardcoded "Md Sayed Alve" thread + fake "Page N highlight" annotation — and replaced it with an honest, data-free guide to the real tools. (The definitive comment list is the embedpdf `CommentsSidebar`, which must render inside the annotation provider tree and so cannot be mounted from this shell.) **Sticky-note placement/editing and text-comment placement are interactive → verify in the running app.**
- **Phase 13 (pen / drawing) — real bug fixed:** Draw called the signature bridge's `activateDrawMode`, which activates the deliberately-separate `"signatureInk"` capture pen and flips the viewer into signature **placement** mode (a different workflow) — and it no-ops when the signature layer isn't mounted, so the Draw button effectively did nothing. Rewired to the real `"ink"` (= "Pen") annotation tool, which stores freehand strokes in the existing annotation state (INK subtype) and stays armed for consecutive strokes. Ordering matters: `signature.deactivateTools()` sets the annotation active tool to null, so we deactivate signature **first** and activate `"ink"` **last** (activate-last wins). **Verify drawing + Escape-to-cancel in the running app.**
- **Phase 14 (tool lifecycle & Escape) — de-duplicated:** The ViewerShell keydown handler had a second `Escape → setTempTool(null)` that competed with `useToolLifecycle`'s capture-phase Escape handler (which already owns temp-tool cancel → search-close → double-Escape-to-view). Removed the duplicate; ViewerShell's Escape now only closes **search** (its own state — `setShowSearch(false)`, mode→view, clear query), guarded on `showSearch`. Mode switches already cancel incompatible temp states because `useToolLifecycle.setMode` nulls `tempTool` on every mode change → the annotation effect's `else` branch reverts to the passive `select` tool and deactivates signature. So: nothing stays stuck, Escape has a single predictable owner, and switching modes cancels temp tools. **Verify Escape/mode-switch flows in the running app.**
- **Phase 15 (edit mode) — wired to real ops:** Passed `onToolSelect` into `ContextualToolbar` (it was declared but never provided, so Add Image / Advanced Edit were dead). **Add Text** = `tempTool "text"` → real FREETEXT annotation, PDF stays visible. **Add Image** = `onToolSelect("addImage")` → the real `createStampTool`-based image tool; `addImage` is in `EmbedPdfViewer`'s `isInAnnotationTool` set, so it overlays the viewer with the PDF still visible. **Advanced Edit** re-pointed from the phantom id `"editPdf"` (which exists nowhere in the codebase — the button was dead) to the real registered `"pdfTextEditor"` tool (`tools/pdfTextEditor/PdfTextEditor.tsx`, a full in-app content editor with its own view + sidebar). ## Phase 20–23 notes (organize suite: select / reorder / rotate / delete)

Investigation confirmed the four Organize operations were already largely real — each mutates the local working set (`internalPages`) and, crucially, the whole set commits to the actual PDF through a single **Apply Changes** button → `ViewerShell.onApply` → `applyOrganizeChangesLocal` (rebuilds the document via `@cantoo/pdf-lib` `copyPages`) → `actions.consumeFiles`. The genuine gap was **discoverability of the commit**: nothing signalled that edits were pending, so a user could reorder/rotate/delete and never realize they had to click Apply — exactly the "only reorders the UI cards" trap Phase 21 warns against. All edits are in `workbench/viewer/OrganizeMode.tsx` plus a robustness fix in `services/offlinePageOps.ts`; no new page-op machinery.

- **Phase 20 (page selection) — already real, polished:** Clicking a page selects it (clear `.selected` accent border + ring + checkbox); Ctrl/Cmd-click toggles into a multi-selection; Shift-click selects a contiguous range from the anchor; Shift+Ctrl extends the range additively (`handlePageClick`, real anchor tracking). The selection drives the action toolbar (Rotate/Duplicate/Delete/Extract enable only with a selection) and the header selection pill, so selection stays synchronized with the toolbar. Polished the card `aria-label` to announce the **working position** and provenance ("Page 3 (from original page 1), selected") instead of an internal id.
- **Phase 21 (reorder) — real commit, labels now update:** Dragging a thumbnail shows a drop-position indicator (`.drag-over` accent double-ring), and releasing reorders `internalPages` (`handleDrop` splices out the dragged page and inserts at the target). This is **not** cosmetic: the new order is written to the real PDF on Apply (`copyPages` copies source pages in the working order). Added **position-based page labels** — the footer now shows the page's live 1-based position (renumbering as pages move) with a subtle "from N" hint when a page's position differs from its original source, satisfying the plan's "page labels update" step while preserving traceability.
- **Phase 22 (rotate) — real, integrity-hardened:** Rotate Left/Right rotate **only** the selected pages (`handleRotate` applies `(rotation + delta + 360) % 360` to the selected set; per-card quick-rotate for a single page). The rotation is visible immediately (CSS `transform: rotate()` + a degree badge) and is applied to the real document on Apply. Hardened `applyOrganizeChangesLocal` so the per-page rotation stays **aligned to the correct copied page**: it now builds paired `{index, rotation}` entries and filters them together (previously the index list was filtered while the rotation list was not, which could desync rotations under an out-of-range entry). Normal use never hits that edge, but the code is now robust regardless of input.
- **Phase 23 (delete) — real, with a confirm + empty guard:** Delete removes the selected pages from `internalPages` (`handleDelete`) and clears the selection; the thumbnails, count, and (now position-based) numbering all update. Deleted pages are genuinely dropped from the rebuilt document (they are simply omitted from the `copyPages` order). Added the plan's "confirm where appropriate": **Apply now prompts for confirmation whenever the commit would permanently remove pages** (`removedCount > 0`), and Apply is **disabled when the working set is empty** so the user can't attempt to commit a zero-page document (which `applyOrganizeChangesLocal` rejects).
- **Cross-cutting — dirty-state commit affordance:** Added `isDirty` (working signature ≠ pristine `1:0,2:0,…`), `isEmpty`, and `removedCount` derivations plus a single `handleApply`. The two Apply buttons were consolidated onto this handler: **Apply Changes goes solid-accent with a "Unsaved changes" flag when there are pending edits**, is disabled (muted) when there is nothing to commit or the doc is empty, and routes destructive commits through the confirm. This makes the working-copy → real-document bridge obvious and closes the "edits look applied but never reached the PDF" gap. **All Organize interactions (select/reorder/rotate/delete + Apply committing to the real document, and the confirm-on-delete) are interactive → verify in the running Windows app.**

## Phase 24–27 notes (organize suite: extract / insert / replace / split)

These four are the "import/export a whole file or spawn new files" Organize actions. The audit found Extract already real, Split correctly served by the app's existing Split tool, and Insert/Replace pointed at semantically-wrong tools — so Insert/Replace got **new local pdf-lib ops** (no cloud, no separate window) while Split and Extract were confirmed/relaxed. All UI edits are in `workbench/viewer/OrganizeMode.tsx`; the commits live in `workbench/viewer/ViewerShell.tsx`; the new page ops are in `services/offlinePageOps.ts`.

- **Phase 24 (extract) — already real, verified:** Selecting pages and clicking **Extract** runs `ViewerShell.onExtract` → `extractPagesLocal(file, "…")` (local `@cantoo/pdf-lib` `copyPages`) → the result is added as a **new file** and made active (`actions.addFiles({selectFiles:true})` → `setActiveFileId`), then Organize closes. It produces a real output PDF of exactly the selected pages — no fake success message. Left as-is (already satisfied the exit criterion).
- **Phase 25 (insert) — new local op, no cloud:** Insert previously opened the backend **Merge** tool (a cloud endpoint, violating "No cloud dependency"). Rewired: the Insert button opens a **local hidden file picker** (`<input type=file accept=application/pdf>`, reused for Insert+Replace via a `pendingSourceAction` ref). On choosing a PDF, `OrganizeMode` computes a 0-indexed insertion position (**after the last selected page, or the end** if nothing is selected) and hands the chosen `File` + position + working-page snapshot to `ViewerShell.onInsert`, which **bakes any pending working edits** into the base via `applyOrganizeChangesLocal` (so the index matches what's on screen), then calls the new `insertPagesLocal(base, source, at)` and commits with `actions.consumeFiles`. It **stays in Organize**, so the file-sync effect rebuilds the working set and the new pages + count refresh in place. New pages appear in the actual document (exit criterion met).
- **Phase 26 (replace) — new local op, no cloud:** Replace previously opened `reorganizePages`, which only shuffles pages **within one document** and cannot import from another file. Rewired to the same local picker; `OrganizeMode` passes the chosen `File` + the **0-indexed working positions of the selected pages** to `ViewerShell.onReplace`, which bakes pending edits, then calls `replacePagesLocal(base, source, selectedIndices)` — the source pages are spliced in at the first selected position and all selected pages are dropped — and commits via `consumeFiles`, staying in Organize so thumbnails/state refresh. The actual document then contains the replacement pages (exit criterion met). Button stays gated on a selection.
- **Phase 27 (split) — defers to the real Split tool:** Split correctly routes to the app's existing **Split** tool (`onToolSelect("split")`), which exposes the genuine supported methods (`useSplitOperation` → `SPLIT_ENDPOINTS`: by pages / sections / size / page-count / doc-count / chapters / page-divider / poster) and produces real output files (ZIP → `extractZipFiles`). Per the governing directive we reconnect to the real implementation rather than build a fake one. Only change: the Split button's gate was relaxed from `disabled={!hasSelection}` to `disabled={!file}` — Split has its own options and does not require a page selection in Organize, so the old gate was misleading. (Split's outputs depend on the app's Split backend, same as the standalone Split tool.)
- **New service functions (`services/offlinePageOps.ts`):** `insertPagesLocal(baseFile, sourceFile, insertAtIndex)` and `replacePagesLocal(baseFile, sourceFile, selectedIndices)` — both accept `File | Blob`, preserve page rotations, and return a new PDF `Blob` via `PDFDocument.create` + `copyPages` + `addPage` + `save`, matching the existing extract/apply pattern. Fully offline.
- **Verification:** Source-level (identifier resolution, prop-signature match across `OrganizeMode`↔`ViewerShell`, no stale `onInsert(pids)`/`onReplace(pids)`/merge/reorganize routing). **Interactive → verify in the running Windows app:** picking a source PDF for Insert/Replace, insertion position, replacement result, page-count/thumbnail refresh in place, and that Split opens the real Split options.

## Phase 28–31 notes (merge, search, bookmarks, tabs)

These four reconnect **already-complete** real implementations that the reskin shell had left orphaned or unfed — no new engines were built. Edits are in `workbench/viewer/ViewerShell.tsx`, `workbench/viewer/RightUtilityPanel.tsx`, `components/viewer/SearchAPIBridge.tsx`, `contexts/ViewerContext.tsx`, `data/useTranslatedToolRegistry.tsx`, `components/layout/Workbench.tsx`, and `workbench/home/QuickTools.tsx`.

- **Phase 28 (merge) — orphaned host reconnected:** The root cause was structural: in the reskin, registry tools render through `RightSidebar → ToolPanel → ToolRenderer`, but **`RightSidebar` is never mounted**, so selecting Merge (or any registry tool) set `selectedTool` with nowhere to render — a permanent "dead card." Merge itself (`tools/Merge.tsx`) is a complete, working component (`useMergeParameters`/`useMergeOperation`, ≥2-file guard, real sort + execute). Fix is a pure reconnection: (1) `Workbench.tsx` `case "fileEditor"` now renders the real `ToolRenderer` in a right-docked panel beside `FileEditor` whenever a tool with a `component` is selected; (2) the Merge registry entry gets `workbench: "fileEditor"` so selection routes to that workbench (Merge's own self-switch becomes a redundant safety net); (3) the Home "Combine Files" card's dead `id: "combine"` was corrected to `id: "merge"`. **Interactive → verify in the running app:** open ≥2 PDFs, pick Merge, confirm the panel appears and merging produces one combined document.
- **Phase 29 (search) — shell now re-renders on results:** The count math and dedup/hidden-rect filtering in `SearchAPIBridge` were already correct; the bug was that `ViewerShell` reads `getSearchState()` from a bridge **ref during render** but nothing re-rendered it when new results arrived, so "N results" and the active index could stay at 0/stale. Added a search immediate-notifier to `ViewerContext` (mirroring the existing zoom/scroll/pan notifiers), fired from `SearchAPIBridge` **right after** the context search ref is refreshed (race-free), and consumed by a force-rerender subscription in `ViewerShell`. The correct count formula and dedup logic were left untouched. **Interactive → verify in the running app:** searching shows the true match count and the active-match index advances with next/previous.
- **Phase 30 (bookmarks) — real outline fed + a CSS clip fix:** The `RightUtilityPanel` outline tab has a complete recursive tree renderer but was receiving **no `bookmarks` prop** (previously hardcoded fakes, then emptied), so it always showed the empty state. `ViewerShell` now fetches the real outline via `bookmarkActions.fetchBookmarks()` when a document loads (with a brief retry because the bookmark bridge registers only once the document is ready), maps embedPDF's `PdfBookmarkObject` tree into the panel's flat `BookmarkItem` shape using the same page rule as `BookmarkSidebar.resolvePageNumber` (0-based `pageIndex + 1`; section headers without a destination borrow their first child's page), and passes `onBookmarkNavigate={(b) => scrollActions.scrollToPage(b.page)}`. - **Phase 31 (tabs) — closing the active tab keeps you in the viewer:** `activeFileId` lives in `ViewerContext`, and the `REMOVE_FILES` reducer (FileContext) never touches it — so closing the **active** tab left `activeFileId` pointing at a deleted file and the viewer fell back to Home even with other documents still open. `handleTabClose` now, when the closed id is the active one and siblings remain, selects a neighbor (prefer the tab to the right, else the left) via `setActiveFileId` **before** removing; `onClose()` (return to Home) is reserved for closing the final tab. Mirrors the real `DocumentTabBar.handleTabClose` sibling-selection logic. **Interactive → verify in the running app:** open 3 docs, close the active one, confirm a sibling becomes active (no bounce to Home) and closing the last returns Home.

## Phase 32–35 notes (position persistence, tool discovery, reader controls, right utility area)

These four continue the pattern: reconnect real, already-existing capabilities to the reskin shell and make the honest state visible, rather than build fakes. Edits are in `workbench/viewer/ViewerShell.tsx` (Phases 32/34/35), `workbench/viewer/ContextualToolbar.tsx` (Phase 34), and `workbench/home/QuickTools.tsx` (Phase 33). - **Phase 32 (document position persistence) — real save/restore of page + zoom:** The viewer never remembered where you were in a document across close→reopen. Added a **stable persistence key** independent of the volatile `fileId` — `pdf-elite:pos:${name}|${size}|${lastModified}` (the same identity `StirlingFile.quickKey` uses), so it survives reopening the same file. A **save effect** (keyed on `currentPage`/`zoomScale`) writes `{page, zoom}` to `localStorage` on change and on `beforeunload`; a **restore effect** (keyed on the active file) reads it back and, because the embedpdf document isn't scrollable the instant a file becomes active, **retries until `getScrollState().totalPages > 0`** (≤40×150ms) before calling `scrollActions.scrollToPage(clampedPage)` (clamped to the real page count, only when target>1) and best-effort `zoomActions.setZoomLevel(savedZoom)`. No renderer change; it drives the same canonical scroll/zoom actions every other control uses. **Interactive → verify in the running app:** scroll to page N, zoom to X%, close the tab and reopen the same file, confirm it returns to ~page N at ~X%.
- **Phase 33 (existing tool discovery) — dead "All Tools" button made real (progressive disclosure):** The Home Quick Tools header had an **"All Tools" button that did nothing**.
